# Jarvis iOS

A native SwiftUI chat client for the Jarvis backend: text chat over `/chat`,
streaming tool-call progress, Copy buttons for drafted messages, and an approvals
view for calendar changes that need Ben's sign-off before they apply.

## Project structure

The Xcode project (`Jarvis.xcodeproj`) is generated by
[XcodeGen](https://github.com/yonaskolb/XcodeGen) from the committed spec,
`project.yml` — don't hand-edit project settings in Xcode; change `project.yml` and
regenerate instead.

```
ios/
  project.yml              XcodeGen spec (bundle id, signing team, fonts, ATS exception)
  Jarvis/
    JarvisApp.swift         App entry point
    ContentView.swift       Top-level layout: header, message log, composer
    ChatViewModel.swift     Talks to the backend (/chat, /apply), owns session state
    ChatModels.swift        Codable request/response/message types
    ComposerView.swift      Text input + send button
    MessageBubble.swift     Chat bubble (user / Jarvis / error / draft-copy)
    ApprovalsBubble.swift   Renders pending approvals with an Approve button each
    HeaderView.swift        Animated header mark, reflects headerActivity
    CalculatingRing.swift   The "thinking / processing" ring animation
    Theme.swift             Colors, fonts (Orbitron + JetBrains Mono)
    Fonts/                  Bundled .ttf files registered via UIAppFonts
  scripts/
    deploy-to-iphone.sh     Build + install + launch on a connected iPhone
```

## Setup

```bash
cd ios
xcodegen generate
open Jarvis.xcodeproj
```

Point the app at your backend by editing `backendBaseURL` in
[`Jarvis/ChatViewModel.swift`](Jarvis/ChatViewModel.swift) — by default it's the Pi's
Tailscale hostname (`http://raspberry-pi:8000`). The backend is plain HTTP over the
private tailnet, so `project.yml` sets an ATS exception (`NSAllowsArbitraryLoads`) to
allow that; this won't work over the open internet or in an environment that blocks
arbitrary-loads HTTP.

Requires a physical iPhone (iOS 17+) — there's no calendar/Trello data to show in the
simulator. Signing uses `DEVELOPMENT_TEAM: 749Y7LB6WB` (automatic signing) in
`project.yml`; change that if you're building under a different Apple Developer
account.

## Deploying to a physical iPhone

`scripts/deploy-to-iphone.sh` builds the Debug configuration, installs it, and
launches it on whichever paired iPhone is connected — no need to open Xcode:

```bash
cd ios
./scripts/deploy-to-iphone.sh
```

It finds the first paired device via `xcrun devicectl list devices`, runs
`xcodebuild` into a scratch `scripts/.derivedData/` directory, then
`devicectl device install app` + `devicectl device process launch`. Plug in the
iPhone, unlock it, and trust the Mac first; the script exits with an error if no
paired device is found.

**Redeploy after every change to `ios/Jarvis/`** — the app on the phone is a build
artifact, not something that updates itself. A stale build silently keeps whatever
fields/behavior it shipped with (e.g. a client too old to know about a new field in
the `/apply` payload will just drop that field), which can look like a backend bug
when it's actually an out-of-date phone binary.
